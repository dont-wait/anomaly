# Manual anomaly test dataset

This directory contains the fixture generator and its development-only
EventStoreDB importer. The generator creates a local JSON file; it does not
write to EventStoreDB/MongoDB.

## Generate

From the repository root:

```bash
python3 -m venv tools/test-data/.venv
tools/test-data/.venv/bin/python -m pip install -r tools/test-data/requirements.txt
tools/test-data/.venv/bin/python tools/test-data/generate.py
```

The default command creates:

- 6 source accounts: A-F;
- 8 receiver accounts used by the baseline/probe instructions;
- 30 completed baseline transfer records for A-D and F;
- no baseline transfer records for E; E is reserved for the velocity burst;
- random baseline timestamps between 07:00 and 22:00 Vietnam time, with
  variable daily counts and at least 30 minutes between transfers per source;
- no probe transactions, because those are performed manually;
- seed `20261110` and a reference time (end of the history window) of one
  hour before the command runs.

The history therefore ends shortly before you probe: the 7-day mean, 24-hour
counts and time since the previous transfer reflect recent activity, while the
2-minute, 5-minute and 1-hour velocity windows are still empty. Probe soon after
importing; the older the history gets, the more every account looks dormant.
The reference time is written to the JSON; pass it back with
`--reference-time` to regenerate the same fixture.

The output is written to `tools/test-data/output/anomaly-a-f.json`, which is
ignored by Git because it contains local test credentials.

For a given seed and reference time the schedule is reproducible and different
for each account. Days without
transfers are possible, not guaranteed. This changes baseline timestamps only;
the manual velocity probe for E still uses 15-second intervals.

Run the offline generator tests:

```bash
tools/test-data/.venv/bin/python -m unittest discover -s tools/test-data
```

If you already imported an older fixture, do not import a regenerated fixture
over it: the stable transfer IDs will conflict with changed timestamps. Because
the default reference time follows the clock, every run without
`--reference-time` produces new timestamps. Keep
the original fixture for that environment; use a fresh isolated test environment
for the new schedule. Regenerating JSON does not update stored events.

Use another seed, reference time, or output path when needed:

```bash
tools/test-data/.venv/bin/python tools/test-data/generate.py \
  --seed 42 \
  --reference-time 2026-11-10T12:00:00Z \
  --output /tmp/anomaly-a-f.json
```

## Cases

| Account | Case | Manual probe described in the JSON |
| --- | --- | --- |
| A | `normal` | 20,000 VND to the familiar receiver, on the familiar mobile device/channel |
| B | `amount_spike` | 100,000 VND to the familiar receiver (5x the typical 20,000 VND) |
| C | `new_receiver` | 20,000 VND to a receiver not present in C's baseline |
| D | `new_device` | 20,000 VND from a new device, with familiar receiver/channel |
| E | `velocity_burst` | 6 manual requests, 15 seconds apart; expected positive label starts at request 3 |
| F | `contextual_amount` | 100,000 VND through the less-used web channel to a new receiver, using the familiar device |

The JSON is a dataset contract for the development/test importer. It is not
safe to import by directly inserting MongoDB documents: the importer creates
canonical history through EventStoreDB.

## Import into the local banking stream

After generating the fixture, run the development-only importer from `server/`:

```bash
cd server
APP_ENV=development \
SEED_DEMO_ENABLED=true \
SEED_ANOMALY_ALLOW_TARGET=true \
make seed-anomaly-data
```

The importer creates the accounts, marks them KYC verified, funds their
post-baseline balances, and appends `TransferCreated`/
`TransferCompleted` historical events to EventStoreDB. It does not write
MongoDB directly. Start the banking projector and relay afterwards so MongoDB
projections and model feature state catch up:

```bash
make start-worker
make start-relay
```

To make the command wait before declaring the fixture ready, run the command
directly with a timeout after the projector and relay are running:

```bash
APP_ENV=development \
SEED_DEMO_ENABLED=true \
SEED_ANOMALY_ALLOW_TARGET=true \
go run ./cmd/seed-anomaly-data -wait-for-ready 2m
```

Readiness requires both the `banking-projection` checkpoint and the relay's
`model_feature_progress` revision to reach the imported EventStoreDB revision.
Without `-wait-for-ready`, the manifest is still marked `in_progress` until
the import itself completes; do not test until projection and feature
readiness has been checked.

The importer writes `anomaly-a-f.imported.json` beside the fixture. It contains
the actual account numbers generated by the backend and is ignored with the
fixture output directory. The manifest is `in_progress` while importing and
becomes `complete` only after all events are appended and optional readiness
checks pass. If an import is interrupted, do not test; rerun the same fixture
to resume idempotently, or discard the isolated environment. The stable balance
marker prevents a rerun from restoring an account balance after a manual probe.
Historical baseline `TransferCreated` events update feature state but are not
published to the live Kafka risk-scoring topic.
